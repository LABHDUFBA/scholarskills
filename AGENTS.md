# Instructions for agents working on ScholarSkills

## Purpose and authority

ScholarSkills is a research-method catalogue, not a collection of unchecked prompts. The human researcher and maintainers decide methods, authorship, rights, review status and publication. Read `README.md`, `registry/EDITORIAL_POLICY.md` and `CONTRIBUTING.md` before changing a package. For a specific skill, read its `SKILL.md`, `README.md`, methodological references and tests.

## Source of truth

- `registry/registry.json` holds current IDs, slugs, availability, maturity, DOIs and citations. `registry/metadata-schema.json` defines entry fields. Do not infer current status from older deployment reports or the archived Zenodo version.
- One Git repository holds multiple skill packages. Each available skill has its own directory and archival identity. `skill-template/` is a scaffold, not a released skill. Planned registry entries are not implementations.
- `site/` is generated by `scripts/build_site.py`; do not hand-edit generated skill pages. If the registry or generator changes, regenerate the site and check it with `python3 scripts/build_site.py --check`.

## Before and after an edit

1. Verify the canonical remote, branch, working tree and target files. Work on a dedicated branch; do not push, open a PR, merge, tag, publish or deposit without an explicit request from the operator.
2. Preserve existing work. Change only the requested files and their necessary generated derivatives; do not silently rewrite historical logs or archived snapshots.
3. For a new skill, start with `skill-template/`, propose an ID in the PR, and follow `registry/EDITORIAL_POLICY.md`. One skill per PR unless maintainers request otherwise. State the method, assumptions, input/output, stop criteria, tool failures, ethical limits and provenance. Use only synthetic or public data in examples and tests.
4. Run the package's structural validator and its own test suite. Report exactly what passed and what was not tested. A structural pass or green CI does not validate scientific fidelity, citations or empirical conclusions.
5. Check `git diff --check`, review the changed-file list and verify links and registry references before handing work to a reviewer. Never represent a local edit as a merged or released change.

Example checks (from the repository root):

```bash
python3 scientific-agent-skill-development/scripts/validate_skill.py scientific-agent-skill-development
(cd scientific-agent-skill-development && python3 -m unittest discover -s tests -v)
python3 scripts/build_site.py --check
git diff --check
```

For other packages, substitute their directory and read their `README.md` for dependencies and test commands. The CI checks multiple packages on Python 3.10 and 3.12; do not infer that a local check on another version is equivalent.

## Evidence, safety and rights

- Distinguish source-backed fact, interpretation, hypothesis and proposal. Verify citations against the cited material before making methodological claims. Mark unverified claims explicitly.
- Never commit credentials, raw private data, reidentifiable records, unlicensed third-party content or internal-only files. Review examples and generated artefacts before staging them.
- Preserve existing DOI and version metadata unless the operator supplies an independently verified correction. A `main` branch change does not update an archived Zenodo record.
- The root and package `LICENSE` files apply MIT to the project's original code and associated documentation. Preserve existing copyright notices. Third-party fonts, logos, trademarks, images and other external assets need separate rights review; their presence here does not grant MIT rights to them.
- Do not claim `peer-reviewed` or `replicated` without the records required by the editorial policy. Record environment, dependencies, commands and actual test results when changing maturity claims.
