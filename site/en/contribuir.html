Contribute a skill

A skill here is a package that describes a research method, runs tests and can be cited. To propose one you do not need to write code alone: fill the brief and hand it to your agent — the SS-0000 protocol does the rest.

Download the brief (.md)Read the contribution guide

Three ways to propose a skill

You do not need to know Git to start, and you do not need to write code alone. Preparation can be done with an agent; the editorial decision remains human.

  1. 1
    Prepare the package with an agent

    Download the Markdown brief and ask your agent to fill in what you know. An empty field is a question to ask, not a gap to invent. Protocol SS-0000 can support preparation and structural validation; it does not replace human checking or editorial review.

  2. 2
    Open a pull request

    One package per pull request, with one new entry in registry/registry.json. Propose the SS-NNNN identifier in the description; maintainers assign the final one. Run the package validator and tests before submitting.

    Read the contribution guide

  3. 3
    Do not use Git? Ask for guidance

    Write to the laboratory and describe the skill you want to propose. The team advises on the format and points to a submission route; there is no promise of email submission or automatic acceptance.

What review checks

  • The problem, the research stage and the discipline the skill serves are stated.
  • Every execution requirement is listed: credential, environment variable, software, network.
  • A limits section exists: what the skill does not do and does not prove.
  • Tests run offline and tests/RESULTS.md carries the real environment, command and output; integration with real services, where it exists, is documented separately.
  • No credential, local path or personal data in the package.
  • Licence and authorship are explicit, and the citation matches the real record.

How review happens

First, a structural triage: the package validates against the catalogue schema and the Agent Skills specification. Then two people apply the editorial policy criteria and record a verdict per dimension. The decision can be accept, return for corrections or reject; the report is recorded, and the author's response stays in the pull request.

Corrections after publication produce a new version with a CHANGELOG.md entry. DOI deposits require explicit authorisation from the maintainers. The project's internal review is not presented as assessment by an external body.
