Evidence and maturity

Six independent dimensions, what each requires and what the catalogue records today.

Evidence is not a ladder

The previous version of the portal presented four levels in sequence: experimental, tested, peer-reviewed, replicated. The sequence is useful vocabulary, but it suggests that a package climbs steps and that the top step covers the ones below. It does not. A package can have solid functional tests and no methodological assessment; it can be re-executed by third parties without having been peer-reviewed.

The catalogue therefore treats evidence as independent dimensions. None is granted automatically; each requires the artefact that supports it.

Structural conformance

Validator applied, specification version and result recorded.

Functional tests

Positive, negative and edge cases; environment, result and date recorded.

Methodological assessment

Protocol, benchmark, adequate metrics and limitations.

Peer review

Editorial policy, authorised reports, version and decision.

Independent re-execution

Non-author executor, environment, version, results and divergences.

Scientific replication

Where applicable, assessment on new data or a new study under a defined protocol.

Re-execution is not replication. Computational re-execution checks whether the same code, in the same environment, produces the same result. Scientific replication assesses whether the finding holds on new data or in a new study under a defined protocol. The distinction follows the NASEM report Reproducibility and Replicability in Science (2019); terminology varies across disciplines.

Editorial status, DOI and evidence

Editorial status (planned, available, deprecated) describes the record's situation in the catalogue. Maturity describes what has been documented about the package. A DOI identifies an archived deposit; it does not certify scientific quality. An offline test with fixtures does not demonstrate performance against a real API, and an integration test does not demonstrate that the agent conducts the task end to end.

The tests recorded in the packages are mostly automated and offline. They exercise positive, negative and edge cases of the code; they do not replace peer review or independent re-execution. The editorial policy defines what each record requires and how corrections are versioned.
